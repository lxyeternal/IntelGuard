The rise of supply chain attacks has cast a long shadow over the cybersecurity landscape. These attacks, where malicious code infiltrates software dependencies, pose a threat to developers and organizations alike, particularly when using committed vendor directories. Let’s explore the vulnerabilities and potential solutions to secure your Go projects.
Supply Chain Attacks
Software supply chain attacks inject code into an application in order to infiltrate users of the app. Notable recent examples include:

Codecov Attack (2021) : In this attack, the Codecov code coverage tool was compromised, allowing attackers to steal sensitive information such as credentials and secrets from Codecov users.
Log4j Vulnerability (2021) : This widespread vulnerability in the Log4j logging library allowed attackers to remotely execute arbitrary code on affected systems. Due to the ubiquitous nature of Log4j, this vulnerability impacted a vast number of applications and software products.
SolarWinds Orion Attack (2020) : One of the most sophisticated and far-reaching supply chain attacks, where malicious code was inserted into the SolarWinds Orion software update mechanism. This breach affected numerous high-profile government and private sector organizations, allowing attackers to spy on internal email traffic and exfiltrate sensitive data.
NotPetya Ransomware Attack (2017) : Initially spread through a compromised update mechanism of a widely used Ukrainian accounting software, NotPetya masqueraded as ransomware but was primarily designed to cause disruption. It quickly spread globally, causing billions of dollars in damages to major corporations by rendering their computer systems inoperable.
CCleaner Incident (2017) : In this attack, hackers breached the popular PC cleaning tool, CCleaner, by inserting a backdoor into its download server. This allowed the attackers to potentially take control of the systems of millions of users who downloaded the tainted version, targeting large technology and telecommunications companies specifically.
Go Dependency Management
Go projects rely on a web of dependencies, both direct and transitive. A compromised dependency, however small, can open the door to data breaches and manipulation of operations. This risk is amplified in larger organizations with complex software ecosystems.
Go Vendor Directories
While vendor directories offer the convenience of storing dependencies within a project’s repository and making it self-contained, they create a security loophole. The go mod verify command is designed to ensure that the modules on which your project depends have not been altered since their download. It accomplishes this by comparing the current modules’ cryptographic hashes against a recorded set in the go.sum file. However, this verification process applies solely to modules stored in the module cache, not to those copied into a project’s vendor directory. This distinction is crucial because while the module cache benefits from an additional layer of security via checksum validation from GOSUMDB, vendored files do not. Consequently, even if go mod verify reports no issues, it doesn’t guarantee the integrity of the code in vendor directories, which can remain unchecked and vulnerable to tampering.
GOSUMDB
GOSUMDB serves as a centralized checksum database that Go uses to verify the integrity and authenticity of modules. However, its protection doesn’t extend to committed vendor directories. This leaves projects relying on vendored dependencies vulnerable to tampering and malicious intrusions.
Industry Seeking Solutions
The Go community actively seeks solutions to this challenge, as evidenced by the ongoing discussion on GitHub (https://github.com/golang/go/issues/27348) . Leading the way, Kubernetes has implemented a custom script (https://github.com/kubernetes/kubernetes/blob/55f2bc10435160619d1ece8de49a1c0f8fcdf276/hack/verify-vendor.sh ) to verify the integrity of its vendor directory. It scrutinizes the content of the vendor directory against the expected state derived from the project’s dependencies as defined in go.mod. This includes checking for unauthorized changes, additions, or removals of files within the vendor directory. Kubernetes thereby adds a layer of security, mitigating the risk of supply chain attacks that might attempt to exploit the vendor directory.
Weighing Risks
The primary risk of committed vendor directories lies in the potential for undetected malicious code injection. This can occur through compromised developer machines or even malicious actors within the team. Without code reviews of vendored files or integrity checks, such vulnerabilities can infiltrate production environments, jeopardizing security.
Strategies for Mitigation
Two main strategies emerge to combat these risks:

Avoiding Committed Vendor Directories: Relying solely on external module sources allows projects to benefit directly from GOSUMDB’s integrity checks. However, this may not be feasible for all build environments or projects with specific dependency management needs.
Implementing Integrity Check Scripts: Adopting a script similar to Kubernetes’ adds a vital layer of security by verifying the integrity of vendored files. While requiring additional effort, this approach offers a balanced solution for projects that necessitate committed vendor directories.
Supply chain security in Go development demands constant vigilance. As cyber threats evolve, understanding and mitigating the risks associated with vendor directories becomes paramount. By adopting the strategies outlined above and staying informed, developers and organizations can build a robust defense against supply chain attacks, ensuring the security and integrity of their Go projects.
