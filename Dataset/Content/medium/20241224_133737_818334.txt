In a recent, sophisticated attack reported by JFrog, .NET developers have been targeted via the NuGet repository, marking the first time attackers have been observed exploiting autorun mechanisms in NuGet packages to distribute malware.
In this blog, we will delve deeper into the details of this unprecedented attack, shedding light on dozens of additional indicators of compromise (IOC) related to the incident and uncovering possible clues to the identity of the attacker.
Autorun Mechanisms in NuGet Packages
Attackers took advantage of autorun features on the .NET platform to quickly deliver their harmful content, creating a significant risk for unaware developers. They used several methods to trick users into downloading their malicious packages, including Typosquatting, misleading package owner names, and manipulating metadata. Some packages even concealed their malicious intent by relying on dependencies. These packages were downloaded a total of 150K times, with the top three packages accounting for a significant portion of downloads before being removed by the NuGet team.
In earlier versions of Visual Studio, developers could place a PowerShell script in a NuGet package’s tools directory, which would automatically run without constraints during specific events, such as package installation or uninstallation. Although Microsoft has deprecated install.ps1 and uninstall.ps1 scripts, init.ps1 scripts are still honored by Visual Studio and run without warnings during NuGet package installation (important to note that the init.ps1 script will not execute automatically while using the NuGet CLI). Furthermore, the init.ps1 script will re-run each time the project’s solution is opened with the Package Manager Console window.
These autorun mechanisms significantly elevate the potential for attackers’ code execution since merely installing the package triggers them. This key factor explains the higher prevalence of malicious packages in the NPM and PyPI ecosystems compared to the Go package ecosystem, where code doesn’t automatically run upon module installation.
Malicious Indicators and Deceptive Tactics
The primary malicious indicator in these packages is the init.ps1 script, which executes upon installation and downloads an .EXE binary to run on the victim’s workstation. This behavior is extremely rare in non-malicious packages, and the “Unrestricted” execution policy should be an immediate red flag. To deceive users into downloading these malicious packages, the attackers employed several methods:

Typosquatting: Creating package names similar to legitimate packages, e.g., “Coinbase.Core” mimicking the legitimate package “Coinbase”.

Malicious dependencies: Some packages do not contain direct malicious payloads but define other malicious packages as dependencies containing the malicious script.

Sophisticated Malicious Payload
Dropper script: All malicious packages observed had the same payload script str, either directly or as a dependency. The payload script modifies PowerShell’s running configuration to allow unrestricted execution of PowerShell scripts.
2nd stage payload: Unlike most malicious package payloads that use open-source hacking tools for quick results, the JFrog Security Research team discovered a custom, low-level language executable payload in this case, indicating a more dedicated attacker. Based on one of the observed 2nd stage payloads, its capabilities include:

Crypto stealer: The payload references the Exodus Lightning wallet app and has embedded Discord Webhooks, suggesting attempts to exfiltrate crypto wallets via Discord webhooks.
Electron Archive Extractor: The payload can extract and execute code from Electron archives using an embedded compiled (Rustlang) copy of Rasar.
Auto-updater: The payload drops a small updater executable at C:\Users\user\AppData\Local\Squirrel-2021\Updater.exe, which checks the original C2 URL for an updated version of the malware.
Further Investigation takes an unexpected turn
The initial report from JFrog exposed 13 malicious packages specifically targeting .NET developers. Intrigued by these findings, we decided to delve deeper into the incident using our retro-hunting system. The results were striking: we discovered dozens of additional packages, many of which contained PowerShell executable scripts and malicious dependencies.

Conclusion
This sophisticated attack on .NET developers underscores the critical need for constant vigilance and adaptation in the face of the ever-evolving cybersecurity landscape. The autorun mechanisms in NuGet packages pose a substantial risk, as they provide attackers with a convenient avenue to execute malicious code. Attackers are likely to continue exploiting this channel of attack, making it imperative for developers and organizations to stay informed and prepared to counteract these emerging threats.
